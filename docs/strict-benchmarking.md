# Strict benchmarking and real-world validation

Patchline should prove usefulness on frozen corpora, not hand-picked demos. The benchmark path is deliberately deterministic: every case has a public source, a human label, a pinned canonical analyzer hash, and a repeatable command.

```bash
go run ./cmd/patchline benchmark-suite examples/benchmarks/strict-migration-corpus.json
```

## What is implemented

`internal/bench` reads `patchline.benchmark-suite/v1` specs and runs the migration analyzer over each pinned case. A case passes only when both conditions hold:

1. The analyzer prediction matches the human label: `safe` or `unsafe`.
2. The canonical migration analysis hash matches `expected_report_hash`.

The runner reports total pass/fail counts plus true positives, true negatives, false positives, false negatives, precision, and recall. Empty expected hashes are rejected, so the suite cannot silently drift when analyzer behavior changes.

```json
{
  "version": "patchline.benchmark-suite/v1",
  "name": "strict-migration-corpus",
  "cases": [
    {
      "id": "billing-bad-backfill",
      "path": "../../demos/billing/migrations/002_bad_backfill.sql",
      "label": "unsafe",
      "expected_report_hash": "0be915737d677c0d06eae943c9293f175c19ca855acb225d93c06de803f39fbe"
    }
  ]
}
```

## Real-world corpus protocol

The intended validation corpus should be built from public, non-proprietary incidents and OSS migrations. Each imported case should include:

| Field | Requirement |
| --- | --- |
| Source | Public URL, commit SHA, release tag, or issue reference |
| License note | Confirmation that the fixture can be redistributed or a script can fetch it |
| Label | `safe` or `unsafe`, assigned before running Patchline |
| Rationale | Short explanation of the observed risk or why the migration is safe |
| Frozen input | Vendored fixture or fetch script pinned to a content hash |
| Expected hash | Canonical Patchline report hash generated by the accepted analyzer version |
| Review record | Human reviewer and date for the label |

Good first sources:

| Corpus slice | Why it is useful |
| --- | --- |
| Rails and Django app migrations | Common backfills, schema changes, and data migrations |
| Postgres extension demos | DDL-heavy compatibility and destructive-operation checks |
| OSS incident postmortems with patches | Grounded unsafe cases tied to actual failures |
| Database migration test suites | Safe negative controls from mature projects |
| Public data-cleanup scripts | Real repair patterns beyond schema-only migrations |

## Anti-cherry-picking rules

1. Freeze a candidate list before scoring.
2. Label cases before running Patchline.
3. Keep false positives and false negatives in the corpus.
4. Report precision and recall, not only pass counts.
5. Pin every input and output hash.
6. Recompute hashes only in explicit analyzer-change commits.

## Design expansion

The current suite benchmarks migration triage. The next strict suites should cover provenance slicing, repair replay, policy gates, and incident bundles:

| Suite | Pass condition |
| --- | --- |
| Provenance slicing | Expected entities, edges, evidence threshold, and slice hash |
| Repair replay | Expected row diffs, effects, scope conformance, and report hash |
| Policy gates | Expected allow/deny result plus per-rule outcomes |
| Incident bundles | Expected bundle entries, hashes, ledger checkpoint, and bundle hash |

This gives Datadog-style users operational evidence that Patchline catches risky repair patterns, while giving RiSE-style reviewers a reproducible artifact for program-analysis and verifiable-repair research.
